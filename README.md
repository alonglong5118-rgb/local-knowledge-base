# Local Knowledge Base

把散落在文件夹里的 Markdown 笔记，变成**可提问、带出处、能自己更新**的私有知识库。

全程自动运行 · 数据不出内网 · 零 API 成本 · 只用标准库

---

## 它解决什么问题

笔记攒到几千份之后，会变成两块死数据：

- **找不到** —— 想找三个月前记的某条结论，只能翻文件夹，或者凭印象搜关键词
- **用不上** —— 内容在硬盘里躺着，不会自己参与任何决策

市面上现成的方案要么把资料全传到云端（涉密内容不能接受），要么按调用次数计费（长期跑成本不可控），要么只做"上传 + 检索"这一步 —— 而真正费时间的其实是**让新内容持续进入检索库**。

这个项目做的是完整闭环：

```
┌─────────────┐   ①摘要    ┌──────────────┐   ③回流   ┌──────────────┐
│ Open WebUI  │ ─────────▶ │  Markdown    │ ────────▶ │  向量检索库   │
│  对话记录    │            │   笔记库      │           │  (Knowledge) │
└─────────────┘            └──────────────┘           └──────────────┘
       ▲                                                      │
       └──────────────── ②每日定时自动触发 ────────────────────┘
```

一次运行完成三件事：**读新对话 → 生成摘要写回笔记库 → 增量同步进检索库**。

## 三个工程亮点

这是本项目与"能跑起来的 demo"的主要区别 —— **它长期运行而没有崩**。

### 1. 三级降级：模型挂了，任务不挂

本地模型调用是最容易失败的一环（进程被 OOM 杀掉、模型没加载完、端口占用）。整个流水线做了三层兜底：

```
本地模型摘要  ──失败──▶  抽取式摘要  ──失败──▶  跳过本次，记录状态
   (质量最好)             (规则抽取前几句)          (下次重跑会续上)
```

**关键点**：降级是**静默但留痕**的 —— 摘要质量会下降，但任务永远不中断，且降级这件事本身会被记录进状态文件，事后能查。

### 2. hash 增量：只处理变过的东西

每次全量重建向量库，在几千份文件的规模上会变成一场灾难（几小时 + 大量重复上传）。

处理方式是：**对每个文件算内容 hash，与上次同步记录的 hash 比对，只上传变化的文件。**

更关键的是**替换而不是追加** —— 内容变更时先把旧文件从知识集合中移除并删除本体，否则知识库里会随每次更新累积重复副本，旧向量会持续污染检索结果。

### 3. 状态留痕：不存在"不知道跑没跑"

定时任务最危险的状态不是失败，而是**悄悄死掉没人知道**，等发现时已经停了一个月。

所有任务统一写状态文件：

```json
{
  "last_run": "2026-01-15T22:03:41+08:00",
  "date": "2026-01-15",
  "sessions": 7,
  "used_llm": true,
  "digest": "30-知识资产/对话精华/2026-01-15.md",
  "build_status": "ok"
}
```

任何一天的运行状态都可回溯：跑了几个会话、走没走降级路径、回落知识库成没成功。异常能在下一次查看时立刻发现。

## 快速开始

### 前置

- Python 3.9+
- 一个 Markdown 笔记目录（Obsidian / 纯文件夹都行）
- [Open WebUI](https://github.com/open-webui/open-webui)（用于向量检索与问答）
- [Ollama](https://ollama.com/)（本地大模型，可选 —— 没有会自动走抽取式降级）

### 安装

```bash
git clone https://github.com/alonglong5118-rgb/local-knowledge-base.git
cd local-knowledge-base
pip install -r requirements.txt   # 只有回流那一步需要 requests
```

### 配置

所有路径都通过环境变量注入，脚本里不硬编码任何绝对路径。

```bash
export VAULT_DIR="$HOME/notes"                          # 笔记库根目录
export WEBUI_DB="$HOME/webui-data/webui.db"             # Open WebUI 的 SQLite 库
export WEBUI_SECRET_FILE="$HOME/webui-data/.webui_secret_key"
export WEBUI_BASE="http://localhost:8080"
export WEBUI_ADMIN_ID="<你的 admin user id>"
export WEBUI_ADMIN_EMAIL="<你的邮箱>"
export OLLAMA_BASE="http://127.0.0.1:11434"
```

### 运行

```bash
# 全流程
python3 knowledge_sync.py

# 只生成摘要文件，不做知识库回流
python3 knowledge_sync.py --dry-run

# 补跑某一天
python3 knowledge_sync.py --date 2026-01-15
```

### 挂成定时任务

macOS（launchd，每天 22:00）：

```xml
<!-- ~/Library/LaunchAgents/com.local.knowledge-sync.plist -->
<key>StartCalendarInterval</key>
<dict>
  <key>Hour</key><integer>22</integer>
  <key>Minute</key><integer>0</integer>
</dict>
```

Linux（cron）：

```cron
0 22 * * * cd /path/to/local-knowledge-base && /usr/bin/python3 knowledge_sync.py >> sync.log 2>&1
```

## 内部结构

| 文件 | 作用 |
|---|---|
| `knowledge_sync.py` | 主流程：读对话 → 摘要 → 写笔记 → 触发回流。**仅用标准库** |
| `build_knowledge_base.py` | 笔记库 → 向量检索库的增量同步。需要 `requests` |

`knowledge_sync.py` 刻意只用标准库（`sqlite3` / `urllib`），意味着它可以用系统自带的任何 `python3` 直接跑 —— 定时任务不需要依赖任何虚拟环境，少一个失败点。

---

## 为什么没有用 LangChain / LlamaIndex

不是抵触框架，是这个场景算下来不划算：

| 考量 | 说明 |
|---|---|
| **需求本来就很明确** | 要的就是"读库 → 调模型 → 写文件 → 调 API"，全流程不超过 400 行 |
| **依赖越少越稳** | 这套东西要连续跑几个月无人值守。框架每升一次版，就多一次它悄悄改行为的机会 |
| **调试成本** | 失败时要能一眼定位到是模型没起来、还是 API 报错。中间多一层抽象，排查就多绕一圈 |
| **可控性** | 摘要失败怎么降级、超长文本怎么截断，这些是业务决策，自己做反而更清楚 |

如果将来需求变成"多模型编排 + 工具调用 + 复杂 agent 状态机"，那时再引框架不迟。**框架是手段，不是目标。**

## 已知限制

诚实说明这个项目**做不到**什么：

- **单机方案**，没有做多机 / 集群部署；文件量级到十万级需要换掉 SQLite 换 PostgreSQL + 专用向量库
- **摘要质量依赖本地模型**，4B 级别模型对长对话的要点提取仍会丢细节；降级到抽取式时只有前几句
- **并发度低**，为控制句柄占用是串行上传，首次全量同步几千份文件会慢
- **Open WebUI 的接口没有版本冻结**，升级主版本后需要重新对齐 API 路径

## 设计取舍笔记

几个当时纠结过的点，留个记录：

1. **为什么源库用只读方式打开**（`mode=ro`）—— WebUI 可能同时在写，普通连接会锁库导致两边都失败
2. **为什么每个请求独立连接**（`Connection: close`）—— 长连接在几千次请求下会耗尽文件句柄，进程直接挂掉
3. **为什么单次限制处理条数** —— 不加限制时，某天会话特别多会跑到天亮，而且中途失败要重来；限制单次规模换来"可预期、可重试"
4. **为什么排除历史归档目录** —— 归档区内容陈旧、信噪比低，进检索库会把有用结果的排名挤下去
